# Техническое задание: оболочка для Labwc и NixOS на Rust

Версия: 1.0, проект для согласования. Дата: 15 ноября 2026 года.
Рабочее техническое имя: `mosaic-shell`; окончательное название выбирается отдельно.

## 1. Назначение и согласованные решения

Создать полноценную настольную оболочку для личного компьютера с NixOS и Labwc. Ориентир по составу возможностей — MyDockFinder; визуальный язык самостоятельный, с влиянием macOS: плавающий Dock, компактная верхняя панель, согласованные меню, мягкие скругления и сдержанная анимация.

Пользователь согласовал: полноценную оболочку, Rust, самостоятельный дизайн в mac-подобном стиле, GTK4 с собственной отрисовкой элементов Dock. Реализация начинается после утверждения этого ТЗ. Остальные конкретные решения ниже — предлагаемые инженерные значения по умолчанию, а не ранее согласованные предпочтения пользователя.

Цель версии 1.0 — повседневная работа без сторонних панели, Dock, лаунчера и сервера уведомлений. Labwc сохраняет управление окнами, фокусом, рабочими пространствами и композицией. Оболочка интегрирует существующие системные службы; не заменяет их.

### 1.1. Рассмотренные подходы

| Подход | Преимущество | Цена | Решение |
| --- | --- | --- | --- |
| GTK4 и собственные виджеты | Готовые текст, ввод, меню, доступность и настройки | Эффекты Dock нужно реализовать отдельно | Выбран пользователем |
| Полностью собственный рендеринг | Полный контроль над графикой | Большой объём инфраструктуры текста, ввода и доступности | Не выбран |
| Отдельный рендерер Dock и GTK4 для остального | Гибкая графика Dock | Два графических стека и сложнее сопровождение | Не выбран |

### 1.2. Границы версии 1.0

Входят: Dock, верхняя панель, системный трей, центр управления, сервер и история уведомлений, поиск и запуск приложений, сетка приложений, обои, меню рабочего стола, настройки, интеграция блокировки и завершения сессии, декларативная настройка и упаковка Nix.

Не входят: собственный композитор, файловый менеджер, экран входа, собственная реализация блокировки, магазин программ, облачная синхронизация, совместимость с Windows-программой MyDockFinder, копирование её кода и ресурсов. Файловый менеджер открывается через системные ассоциации. Значки файлов на рабочем столе, история буфера обмена и сторонние исполняемые плагины отложены.

Не являются обязательствами 1.0: глобальное меню произвольных приложений, живые миниатюры всех окон, Mission Control, глобальные жесты тачпада, анимация чужого окна в Dock, изменение оформления всех GTK/Qt-приложений, размывание содержимого за поверхностями. Эти возможности требуют отдельной проверки протоколов или изменений композитора и отдельного решения по объёму.

## 2. Поддерживаемая среда и совместимость

Основная платформа — NixOS, Wayland-сессия Labwc, systemd user, D-Bus. Обязательная архитектура сборки — x86_64-linux; aarch64-linux — дополнительная после проверки на реальном устройстве. X11-сессия не поддерживается; XWayland-приложения внутри Labwc входят в матрицу проверки.

Перед реализацией фиксируются фактические версии NixOS, nixpkgs, Home Manager, Labwc, GTK4, gtk4-layer-shell, Rust, модель GPU и способ запуска сессии. Они пока неизвестны. Минимальная поддерживаемая версия Labwc определяется проверенным набором протоколов, затем закрепляется в README. Нельзя принимать возможности ветки upstream за возможности установленной системы.

Обязательные возможности: wl_compositor, wl_shm, xdg-shell для обычных окон настроек, wlr-layer-shell для оболочки, wlr-foreign-toplevel-management для списка окон и действий над ними. Остальные globals проверяются при запуске. Отсутствие обязательной возможности даёт понятную диагностику; отсутствие дополнительной отключает конкретную функцию.

Все функции имеют состояния: доступны; временно недоступны; не поддерживаются; ошибка. Нет NetworkManager — плитка сообщает причину, остальные компоненты работают. Отключён Bluetooth — это состояние устройства, а отсутствие BlueZ — состояние интеграции. Оболочка не включает службы и не меняет конфигурацию системы без явно заданных опций NixOS.

## 3. Визуальный дизайн

### 3.1. Общие принципы

Собственные значки оболочки и открыто лицензированные ресурсы. Системные иконки приложений берутся из XDG icon theme. Нейтральная палитра, один акцентный цвет, заметный фокус клавиатуры. Названия и состояние понятны без цветового кодирования. Локали первой версии — русский и английский; архитектура локализации допускает другие языки.

Светлая и тёмная темы обязательны. По умолчанию тема тёмная; режим следования системному предпочтению — отдельная настройка. Смена темы не требует перезапуска. Внутренняя тема не меняет настройки чужих приложений. Полупрозрачность опциональна; при её отключении все поверхности остаются читаемыми. Размытие не подменяется захватом экрана.

### 3.2. Начальные дизайн-токены

| Параметр | Значение по умолчанию |
| --- | --- |
| Базовый шаг отступов | 4 логических px |
| Основной текст | 14 логических px, системный sans-serif |
| Высота верхней панели | 32 логических px |
| Иконка Dock | 48 px, диапазон настройки 32–80 |
| Максимальное увеличение Dock | 1,45×, отключаемое |
| Отступ Dock от края | 12 px |
| Скругления | 10 px для меню, 18 px для Dock |
| Минимальная область клика | 32×32 px; у основных кнопок меню 36×36 |
| Анимация меню | 120–180 мс |
| Анимация Dock | 160–240 мс |
| Контраст обычного текста | не ниже 4,5:1 |

Значения уточняются на визуальном прототипе без изменения функций ТЗ. Reduced motion отключает увеличение, прыжки и перемещения; допускает короткое появление без движения. Поддержка масштабов 100, 125, 150 и 200% проверяется фактически; текст и геометрия задаются в логических координатах.

## 4. Функциональные требования

### 4.1. Dock — D01–D12

- D01. Нижнее положение по умолчанию, опционально левый или правый край. Закреплённые приложения, затем незакреплённые запущенные; разделитель; кнопки сетки приложений и корзины.
- D02. Порядок закреплённых меняется перетаскиванием. Добавление и удаление — через контекстное меню и настройки. Desktop ID — основной ключ, путь к бинарнику не является идентификатором приложения.
- D03. Приложения группируются по desktop ID с сопоставлением app_id, StartupWMClass и пользовательских overrides. Неоднозначность не разрешается по одному заголовку окна; доступна ручная привязка. Неопознанное приложение получает запасную иконку.
- D04. Клик по незапущенному приложению запускает его. По приложению с одним окном — запрашивает восстановление и активацию. Повторный клик по активному единственному окну — сворачивание, если включена соответствующая настройка. Несколько окон — список заголовков; выбор запрашивает активацию. Запрос и подтверждённое состояние различаются.
- D05. Контекстное меню: открыть новое окно через desktop action либо повторный запуск, список окон, закрепить/открепить, поддерживаемые desktop actions, закрыть выбранное окно. Закрытие всех окон доступно отдельным явным действием; завершение процесса сигналом не используется.
- D06. Индикаторы: приложение запущено, активное окно, запуск ожидается. Состояние запуска заканчивается при появлении окна либо через 10 секунд с ненавязчивой ошибкой. Значки количества уведомлений не выдаются за универсальный счётчик непрочитанных сообщений.
- D07. Увеличение зависит от расстояния указателя до иконки, плавное, без изменения порядка и дрожания hit-testing. Геометрия поверхности заранее учитывает максимальное увеличение; прозрачные области не перехватывают ввод.
- D08. Режимы: всегда виден с резервированием места; автоскрытие без резервирования. Начальные задержки: показать через 150 мс у края, скрыть через 700 мс после ухода. Пока открыто меню или идёт перетаскивание, Dock не скрывается. IntelliHide по пересечению с окнами отложен: базовый протокол не гарантирует геометрию чужих окон.
- D09. Для скрытого Dock остаётся узкая зона вызова у выбранного края; она не мешает обычным кликам. Поведение у стыка мониторов проверяется отдельно. В полноэкранном режиме Dock скрыт, но может быть вызван настроенным сочетанием; не требует постоянного слоя overlay.
- D10. При переполнении Dock уменьшается до настроенного минимума, затем использует прокрутку. Все элементы доступны клавиатурой; нет выхода за границы монитора.
- D11. Можно перетащить .desktop-файл для закрепления после проверки. Передача файлов в приложения и папки-стеки — после 1.0. Корзина использует GIO/XDG Trash, показывает пустое/непустое состояние; очистка требует подтверждения.
- D12. При hotplug порядок и закрепления сохраняются; исчезновение экрана не создаёт дубликатов приложений и поверхностей.

### 4.2. Верхняя панель — P01–P07

- P01. Слева меню оболочки и имя активного приложения; центр по умолчанию свободен; справа системный трей, индикаторы сети/звука/питания, часы, центр уведомлений и центр управления. Состав и порядок настраиваются.
- P02. Меню оболочки: приложения, домашняя папка, настройки, блокировка, сон, завершение сессии, перезагрузка, выключение. Недоступные действия объясняются.
- P03. Имя активного приложения открывает собственное меню действий над его окнами. Это не меню «Файл/Правка» чужого приложения.
- P04. Часы учитывают системные локаль и часовой пояс. Клик открывает календарь месяца без синхронизации календарных аккаунтов.
- P05. Трей: StatusNotifierWatcher/Host и StatusNotifierItem, иконки, tooltip, Activate, SecondaryActivate, Scroll и контекстное меню через DBusMenu. Изменения и удаление элементов обрабатываются без перезапуска. XEmbed-трей не входит.
- P06. Панель по умолчанию резервирует 32 логических px. При недостатке ширины второстепенные элементы уходят в overflow; часы и доступ к системным действиям остаются достижимыми.
- P07. Рабочие пространства показываются при наличии проверенного поддерживаемого протокола. Его отсутствие не ломает панель; переключение остаётся доступным средствами Labwc. Обязательный выпуск 1.0 не зависит от непроверенного протокола рабочих пространств.

### 4.3. Центр управления — C01–C09

| ID | Модуль | Обязательное поведение |
| --- | --- | --- |
| C01 | Звук | Громкость, mute, выбор выхода и входа, mute микрофона; события внешних изменений |
| C02 | Wi-Fi | Список сетей, состояние соединения, подключение к сохранённой сети, отключение, ввод пароля WPA-Personal |
| C03 | Ethernet | Статус и активное соединение |
| C04 | Bluetooth | Включение адаптера, список устройств, подключение/отключение и pairing с подтверждением |
| C05 | Яркость | Подсветка встроенного дисплея при наличии поддерживаемого устройства и разрешений |
| C06 | Питание | Заряд, зарядка, доступное расчётное время; профиль питания при доступном сервисе |
| C07 | Медиа | MPRIS: название, исполнитель, обложка с лимитами, play/pause, предыдущий/следующий, выбор плеера |
| C08 | Режимы | Не беспокоить, тема, reduced motion |
| C09 | Действия | Заблокировать, сон, выйти, перезагрузить, выключить |

Звук первой версии работает через PulseAudio-совместимый API: PipeWire с pipewire-pulse либо PulseAudio. Непосредственный PipeWire-backend не обязателен. Сеть — NetworkManager D-Bus. Wi-Fi Enterprise, captive portal, редактирование VPN и сложных профилей открываются во внешнем редакторе. Для Wi-Fi нужен корректно реализованный SecretAgent или настроенный внешний агент: один владелец роли, без дублирования запросов. Секреты не сохраняются в конфигурации оболочки; сохранение делегируется NetworkManager и его агенту.

Bluetooth — BlueZ D-Bus и агент pairing только по явно включённой опции; входящие запросы не подтверждаются автоматически. Питание — UPower и logind; профиль — power-profiles-daemon при наличии. Яркость — выбранный в этапе проверки backend через доступный разрешённый интерфейс, без setuid и записи от root из GUI. DDC/CI внешних мониторов отложен; неподдерживаемый ползунок скрывается с объяснением в настройках.

Операции асинхронные: показываются ожидание, успех или ошибка. Ползунок сразу показывает намерение, но после отказа восстанавливает подтверждённое состояние. Частые изменения объединяются. Повторные клики не создают параллельные одинаковые операции. Внешний редактор и его argv задаются декларативно; отсутствие редактора объясняется.

### 4.4. Уведомления — N01–N08

- N01. Собственный сервер org.freedesktop.Notifications: GetCapabilities, GetServerInformation, Notify, CloseNotification; корректные NotificationClosed и ActionInvoked. Объявляются только реально реализованные capabilities.
- N02. Поддерживаются replacement ID, urgency, timeout, actions, безопасное ограниченное форматирование, иконки и изображения с лимитами размера. Разметка и пути приложений считаются недоверенными.
- N03. До трёх баннеров одновременно на выбранном экране; очередь ограничена. По умолчанию обычные баннеры видны 5 секунд, critical — до закрытия. Явный timeout приложения обрабатывается согласно спецификации и пользовательским правилам.
- N04. Центр уведомлений: группировка по приложению, время, закрыть одно, очистить группу и всё. Максимум истории — 500 записей или 7 суток, что наступит раньше. Transient и выключенная пользователем история не сохраняются.
- N05. Режим «Не беспокоить» убирает баннеры, сохраняя разрешённую историю; критические по умолчанию проходят, это настраивается. Есть правила по приложениям.
- N06. На заблокированном экране баннеры и содержимое истории скрыты. При неизвестном состоянии блокировки применяется консервативное скрытие при активации нашей блокировки. Работа с внешним locker проверяется в поддерживаемой конфигурации.
- N07. Действия старых уведомлений не вызываются после потери отправителя или перезапуска сервера; UI обозначает, что действие больше недоступно. Исторические записи не становятся живыми протокольными объектами после перезапуска.
- N08. Если имя D-Bus уже занято другим сервером, оболочка не вытесняет его и сообщает конфликт. Внешний сервер — отдельный режим, в котором собственная история не обещается.

### 4.5. Поиск и сетка приложений — L01–L08

- L01. Общий индекс приложений из XDG_DATA_HOME/XDG_DATA_DIRS, включая пользовательские и доступные Flatpak desktop entries. Учитываются Hidden, NoDisplay, TryExec, OnlyShowIn/NotShowIn относительно среды сессии. Каталог отслеживает изменения.
- L02. Поиск по локализованному имени, имени, ключевым словам и категориям. Ранжирование: точное совпадение, префикс, совпадение слов, нечёткое совпадение; затем закрепление и локальная частота запуска. Частота очищается и может быть отключена.
- L03. Клавиатура: стрелки, Tab, Enter, Escape. Запуск по desktop entry через GIO с корректными field codes и активационным контекстом, где доступно. Нельзя исполнять строку поиска через sh -c. Terminal=true использует явно настроенный терминал и корректный argv.
- L04. Сетка приложений открывается из Dock и сочетанием; категории, поиск, закрепление, прокрутка. Удаление пакетов из сетки не входит в 1.0.
- L05. Быстрые действия: настройки, домашняя папка, блокировка, переключение темы. Калькулятор — ограниченный парсер арифметики без eval и выполнения кода.
- L06. Поиск файлов первой версии — по именам только внутри явно выбранных каталогов. По умолчанию выключен до выбора каталогов; не индексирует содержимое, скрытые файлы, Nix store и удалённые ресурсы. Не следует symlink за пределы корня. Есть отмена, лимит обхода и результатов, исключения и очистка индекса.
- L07. Файлы открываются через GIO/системные ассоциации; поиск работает без файлового индекса. Индексация выполняется в фоне с ограничением нагрузки и не блокирует ввод.
- L08. На каждом seat одновременно один поиск или сетка. Escape и клик снаружи закрывают окно и освобождают keyboard interactivity. Приложение, из которого вызван поиск, не теряет возможность получать ввод после закрытия; восстановление конкретного фокуса запрашивается, где это допустимо.

### 4.6. Рабочий стол и сессия — S01–S09

- S01. Обои на background layer: однотонный фон или локальная картинка, fill/fit/center, настройка по мониторам. Размер декодирования ограничен. Нет зависимости от постоянно работающего swaybg при включённом нашем backend.
- S02. Контекстное меню рабочего стола: домашняя папка, терминал, смена обоев, настройки. Его поверхность располагается в background, обычные окна и панели получают ввод раньше неё. Взаимодействие с меню Labwc не дублируется: выбирается один владелец root-menu.
- S03. Блокировка выполняется проверенным внешним locker, например swaylock. Обычный полноэкранный GTK-виджет не считается блокировкой. Нет собственного хранения паролей или PAM-аутентификации оболочки.
- S04. Сон через logind с учётом inhibitors и полномочий. При настроенной политике lock-before-sleep блокировка должна быть подтверждена поддерживаемым locker прежде запроса сна; неудача не выдаётся за успешную блокировку.
- S05. Выход завершает только управляемую сессию Labwc через проверенный адаптер. Не используется глобальный kill по имени процесса или завершение всех пользовательских сессий. Подтверждение выхода по умолчанию включено.
- S06. Выключение и перезагрузка требуют подтверждения, выполняются через logind и штатную polkit-авторизацию. Оболочка не получает blanket sudo и не сохраняет пароль.
- S07. Системные сочетания регистрируются конфигурацией Labwc, вызывают shellctl. Предложения: Super+Space — поиск, Super+A — сетка, Super+Comma — настройки, Super+N — уведомления, Super+Escape — показать Dock. Включаются опционально и не перезаписывают пользовательские bindings автоматически.
- S08. Индикация раскладки и управление рабочими пространствами добавляются только через проверенные интерфейсы конкретной версии Labwc; глобальный перехват клавиатуры не используется как обход.
- S09. Скриншот — действие через настроенный grim/slurp или portal, с сохранением в выбранный каталог. Запись экрана и собственная реализация portal не входят. Для совместимости приложений документируется конфигурация xdg-desktop-portal-wlr и вспомогательного backend.

### 4.7. Мониторы и ввод — M01–M07

- M01. Верхняя панель по умолчанию на каждом экране. Dock по умолчанию один, на настроенном preferred output; при его отсутствии — на первом доступном экране в стабильном порядке. Возможен режим Dock на каждом мониторе.
- M02. Политика окон Dock: все окна на всех экранах по умолчанию; опция фильтра по output использует события enter/leave. Фильтр по рабочему пространству не обещается без проверенного интерфейса.
- M03. Поиск и системные всплывающие окна открываются на экране вызова: экран кнопки либо output активного окна, иначе preferred output. Глобальные координаты указателя между Wayland-клиентами не предполагаются.
- M04. Отключение монитора закрывает привязанные popup, переносит основной Dock и не теряет настройки отключённого монитора. Поддерживаются разные масштабы и отрицательные взаимные расположения экранов.
- M05. Идентификация выходов хранит connector и доступные метаданные; одинаковые модели без уникального serial требуют явной привязки. Порядковый номер экрана не используется как устойчивый идентификатор.
- M06. Pointer и клавиатура обязательны; сенсорный ввод и multi-seat — вне обязательной матрицы 1.0. Внутренние модели не должны предполагать, что глобальные координаты всегда доступны.
- M07. Только интерактивная поверхность захватывает клавиатуру. Панель и Dock в обычном состоянии не забирают фокус; меню закрывается по Escape, потере релевантной поверхности и исчезновению output.

## 5. Архитектура

### 5.1. Процессы и ответственность

| Процесс | Ответственность | Последствие сбоя |
| --- | --- | --- |
| mosaic-shell | GTK main loop; Dock, панель, popup, поиск, фон, настройки; Wayland-adapter и локальные view models | systemd перезапускает UI; Labwc и приложения продолжают работу |
| mosaic-services | D-Bus backend системных интеграций, сервер уведомлений, история, индекс и хранилище | UI остаётся, показывает reconnect; сервер уведомлений временно недоступен |
| shellctl | Команды существующим экземплярам через session D-Bus | Ошибка команды возвращается вызывающей стороне |

Трей watcher/host принадлежит UI-процессу; после его рестарта элементы должны перерегистрироваться. Неактивные вкладки настроек не запускают свои циклы polling. Падение одного адаптера не останавливает весь backend: ошибка локализуется, подписка восстанавливается с backoff 1–30 секунд и jitter.

Собственные имена D-Bus: org.mosaic.Shell1 и org.mosaic.Services1; окончательно фиксируются после выбора имени проекта. Системные службы доступны через system bus; API оболочки — только session bus. UI работает в GTK main thread; асинхронные операции — вне него. GTK-объекты не передаются между потоками. Очереди ограничены; частые события состояния объединяются, уведомления и команды не теряются молча.

### 5.2. Модули Cargo workspace

`shell-core` — доменные типы, state machines и правила; `shell-config` — схема, валидация, миграции; `shell-wayland` — обнаружение capabilities, outputs, toplevel; `shell-ui` — GTK4 и GSK, виджеты; `shell-services` — интеграции; `shell-storage` — SQLite; `shellctl` — CLI; `shell-test-support` — mocks и fixtures. Точная нарезка crates может быть упрощена, если публичные границы сохранены.

Стек: Rust stable с закреплённым toolchain; gtk4-rs, gtk4-layer-shell, gio/glib, wayland-client и подходящие protocol bindings, zbus, serde/TOML, tracing, SQLite. Версии и лицензии проверяются в этапе 0 и фиксируются Cargo.lock/flake.lock. Tokio допустим для backend; UI получает события через безопасный bridge в GLib main context. Libadwaita не обязательна: стиль и виджеты принадлежат проекту.

### 5.3. Владение Wayland-соединениями

GTK/GDK и gtk4-layer-shell владеют UI-соединением и поверхностями. Отдельное соединение shell-wayland может слушать globals и toplevel, но не передаёт свои wl_surface в GDK и не считает объекты разных соединений взаимозаменяемыми. Активация с seat и токенами проверяется прототипом; допустим ограниченный bridge с минимальным документированным unsafe. Это блокирующая техническая проверка до разработки полного Dock.

Каждое действие над окном адресуется непрозрачным WindowId, уникальным только в пределах compositor epoch. После закрытия окна или потери соединения ID инвалидируется. Нельзя адресовать окно по заголовку. Команды являются запросами: UI принимает итог из событий композитора, а не присваивает состояние оптимистично навсегда.

### 5.4. Контракт внутреннего API

API версионируется суффиксом 1; точный introspection XML фиксируется до реализации соответствующего backend. Базовый контракт:

| Объект | Операции / события |
| --- | --- |
| Shell | ShowLauncher(output_hint), ShowApplications(output_hint), ToggleControlCenter(output_hint), ToggleNotifications(output_hint), ShowDock(output_hint), OpenSettings(section) |
| Config | GetConfig → revision и эффективные значения; ValidatePatch; ApplyPatch(expected_revision, patch); ConfigChanged(revision) |
| Services | GetSnapshot → epoch, revision, состояния и capabilities; StateChanged(epoch, revision, delta); RequestAction(action, args) → operation_id; OperationFinished |
| Diagnostics | GetCapabilities, GetHealth; doctor через CLI |

UI подписывается до получения snapshot, буферизует deltas и применяет только более новые revision; при смене epoch или разрыве последовательности получает snapshot заново. Команда с устаревшим expected_revision отклоняется с Conflict. Ошибки: Unsupported, Unavailable, PermissionDenied, InvalidArgument, Conflict, Timeout, Failed. Полезное сообщение локализуется в UI; машинный код стабилен. Snapshot не содержит Wi-Fi-пароли или другие секреты.

`shellctl`: launcher, applications, control-center, notifications, dock show, settings, reload, doctor, version. Выход 0 — команда принята; ошибка возвращает ненулевой код. Асинхронные операции по запросу имеют режим ожидания результата. IPC недоступен из сети; это не граница безопасности между процессами одного пользователя.

## 6. Данные и конфигурация

### 6.1. Основные сущности

Application: desktop_id, локализованные имена, icon, actions, категории и правила сопоставления. Window: compositor_epoch, handle, app_id, title, outputs, подтверждённые states. Output: доступные идентификаторы, logical size, scale, доступность. Notification: внутренний UUID, session protocol ID, sender, app, timestamp, urgency, безопасный body, actions, transient, состояние. Operation: id, действие, pending/success/error, deadline. RuntimeState: порядок и overrides пользователя, launch statistics и сохранённые настройки.

Конфигурация — TOML с schema_version. Runtime state и история — SQLite в XDG_STATE_HOME/mosaic-shell; кэши и файловый индекс — XDG_CACHE_HOME/mosaic-shell. Миграции транзакционные; резервная копия перед изменением схемы состояния. Неудачная миграция не уничтожает исходный файл. Кэш восстанавливается из источника. Повреждённая история изолируется с диагностикой, UI продолжает работу без истории.

### 6.2. Декларативная и интерактивная настройка

Два режима Home Manager:

1. strict: декларативные значения являются источником истины; управляемые поля в GUI доступны только для чтения. Закрепления и их порядок также управляемы, если объявлены в Nix.
2. defaults: Nix задаёт исходные значения; GUI пишет overrides в отдельный изменяемый файл. Изменение defaults не перезаписывает override. Доступен сброс поля к декларативному значению.

Приоритет: встроенные defaults → конфигурация → разрешённые пользовательские overrides → временные CLI overrides. Секреты не входят ни в один слой. Read-only symlink из Nix store не переписывается. Для изменяемых файлов — атомарная запись и контроль revision; внешний watcher не создаёт цикл перезаписи. Ошибка hot reload оставляет последний корректный конфиг.

Секции: general, theme, dock, panel, outputs, launcher, notifications, integrations, session, privacy, diagnostics. Каждое поле имеет тип, диапазон, default и описание необходимости рестарта. Неизвестные поля и несовместимая версия дают ошибку с путём поля. Изменения темы, размера Dock, списка элементов и задержек применяются без перезапуска; смена владельца D-Bus-сервиса — с управляемым рестартом.

## 7. NixOS и Home Manager

Flake экспортирует packages, devShells, checks, homeManagerModules.default и nixosModules.default. Исходники приложения не скачивают зависимости во время выполнения. Cargo.lock и flake.lock включаются в репозиторий. Основной путь установки — Home Manager плюс опциональный NixOS-модуль для системных зависимостей.

Предлагаемый интерфейс: programs.mosaic-shell.enable, package, settings, configurationMode, enableLabwcBindings, integrations и services. Имена опций фиксируются вместе с кодом модуля; примеры в ТЗ описывают проектируемый API, а не существующие опции nixpkgs.

NixOS-модуль явно включает только выбранные пользователем интеграции и зависимости: NetworkManager, Bluetooth, PipeWire/PulseAudio, UPower, polkit agent, locker, portal backends. Нельзя молча заменить существующий сетевой или звуковой стек. Поставляется минимальный пример системы и отдельный пример подключения к существующей конфигурации.

### 7.1. Жизненный цикл сессии

Один способ запуска каждого процесса. Предпочтительно custom user target mosaic-session.target, привязанный к конкретной Labwc-сессии. Стартовый hook выполняется после появления Wayland socket, импортирует WAYLAND_DISPLAY, DISPLAY при наличии, XDG_CURRENT_DESKTOP и релевантную среду в systemd user/D-Bus activation environment и запускает target. Hook завершения останавливает target; управление закрепляется session wrapper или корректным lifecycle менеджера сессии. Нельзя считать обычный autostart доказательством надёжного shutdown hook.

Обслуживаемая конфигурация 1.0 — одна графическая Labwc-сессия пользователя. Параллельные графические сессии с общей user manager не входят в поддержку. Services привязаны к target; Restart=on-failure, ограничение restart bursts и короткая задержка. Документируется ручной запуск для диагностики без второй копии сервера.

Waybar, сторонний Dock, swaybg, mako/dunst и другой tray watcher отключаются только явными настройками пользователя. Doctor выявляет конфликты ролей; не завершает чужие процессы. Остановка и удаление оболочки возвращает пользователя к обычному Labwc, не меняя его настройки необратимо.

## 8. Производительность, устойчивость и доступность

Числа ниже — цели приёмки, а не результаты измерений. До этапа 1 фиксируется эталонный ПК пользователя, GPU/backend, разрешение и частота, версии пакетов и сценарий нагрузки. Если устройство требует пересмотра бюджета, изменение ТЗ согласуется до реализации дорогой графики.

| Метрика | Цель и условия |
| --- | --- |
| Готовность Dock и панели | ≤ 2 с после старта target, тёплый запуск, p95 из 20 запусков |
| Открытие поиска/меню | ≤ 100 мс до первого кадра, p95 из 100 вызовов |
| Поиск приложений | ≤ 50 мс после ввода, p95, индекс 2000 desktop entries |
| Анимация | ≥ 95% кадров укладываются в 16,7 мс при 60 Гц во время 10-секундного движения по Dock |
| Простой CPU | суммарно ≤ 1% одного логического ядра за 5 минут после прогрева, без анимаций и индексации |
| Память | суммарный PSS процессов оболочки ≤ 250 MiB после прогрева, до 30 окон и 100 уведомлений, без файловой индексации |
| Восстановление UI | ≤ 3 с после однократного аварийного завершения при работающей сессии |
| Длительная работа | 8 часов сценарного прогона без crash; прирост PSS после прогрева ≤ 20 MiB при повторении одной нагрузки |

Нет непрерывного redraw в покое, бесконечного polling или обхода файлов на главном потоке. D-Bus-подписки предпочтительнее опроса. Кэши ограничены, изображения уменьшаются до необходимого размера. Локальные действия имеют deadline; системные длительные операции показывают состояние, допускают отмену, где поддерживается API. Отказ графического ускорения приводит к читаемому упрощённому UI при доступном GTK renderer.

Все пользовательские действия достижимы клавиатурой. У собственных виджетов есть accessible role, name, state и фокус; проверяется AT-SPI. Tooltip не является единственным способом узнать назначение. Учитываются большие шрифты, reduced motion и отключённая прозрачность. Пользовательские заголовки и длинные строки не разрушают разметку.

## 9. Безопасность и приватность

Оболочка работает от обычного пользователя. Нет телеметрии, облачной зависимости и автоматических сетевых запросов для поиска. Журнал не содержит body уведомлений, заголовков окон, Wi-Fi-секретов или содержимого файлов по умолчанию. Debug-лог включается явно, экспорт диагностики показывает предварительный список данных.

Данные истории доступны только владельцу каталога; предлагаемые права каталога 0700, файлов 0600. История отключается и очищается в UI. SQLite не обещает криптографически безопасное стирание или шифрование; это отмечается в документации. Недоверенные иконки, URI, разметка и D-Bus payload ограничены по размеру; SVG не загружает внешние ресурсы. Локальные команды используют структурированный argv, а не shell interpolation. Скачивание и выполнение тем и плагинов не входит.

## 10. Проверка и критерии приёмки

### 10.1. Автоматическая проверка

Обязательны cargo fmt --check, clippy с контролем warnings для своего кода, unit tests доменных правил, интеграционные тесты D-Bus с isolated bus, проверка схемы и миграций, nix build и flake checks. Тесты покрывают поведение: сопоставление приложений, окна и epochs, автоскрытие, конфигурационные конфликты, очередь уведомлений и limits, отказ системных служб, безопасный запуск desktop entries.

Wayland smoke/integration tests выполняются с закреплённым Labwc в nested/headless окружении, где оно поддерживается. Реальный DRM-сеанс и GPU проверяются отдельно: headless не доказывает качество анимаций, lock-before-sleep и multi-monitor hotplug. Визуальные regression checks выполняются с фиксированными шрифтами и темой, допускают согласованный допуск рендеринга.

Версия 1.0 принимается после выполнения обязательных требований и сценариев на поддерживаемой конфигурации. Дополнительные возможности могут быть выключены с явным объяснением; обязательные не заменяются заглушками.

## 13. Риски и решения до реализации

| Риск | Решение |
| --- | --- |
| Версия Labwc не предоставляет нужный протокол | Зафиксировать ограничение; предложить обновление либо явно пересмотреть функцию, не подменять скрытой эмуляцией ввода |
| Активация из отдельного Wayland-соединения некорректна | Проверить на этапе 0 и выбрать безопасный адаптер до строительства Dock |
| GTK/GSK не обеспечивает нужную плавность | Измерить Dock-прототип, сначала оптимизировать собственный виджет; смена стека требует нового согласования |
| Нет надёжного lock readiness у выбранного locker | Выбрать поддерживаемый locker/адаптер; не реализовывать небезопасную имитацию блокировки |
| Существующие службы занимают D-Bus-роли | Явный выбор владельца, doctor и документация миграции |
| GUI и Nix конкурируют за настройки | strict/defaults, независимый override и revision |
| Scope расширяется до собственного desktop environment целиком | Сохранять границы 1.0; файловый менеджер, compositor patches и global menu оформлять отдельно |

До начала реализации понадобятся конфигурация Labwc/NixOS или минимальные сведения о версиях, видеокарте, мониторах и менеджере сессии. Это входные данные этапа 0, а не причина оставлять неопределёнными функции ТЗ. Их фактические значения пока не известны.
